# 名刺管理アプリケーション

営業担当者向けの名刺管理アプリです。名刺画像の取り込み → AI 読み取り → 確認・修正 → 登録 → 検索・詳細表示までを、1つの Nuxt アプリ（フロント + サーバー API）で提供します。シングルテナント・PC ブラウザー前提です。

## 環境の立ち上げ手順

前提: Node.js 24 / npm

```bash
npm install
cp .env.example .env   # 値を設定する（下記）
npm run dev
```

ブラウザーで http://localhost:3000 を開きます。

`.env` に設定する値:

| 変数 | 内容 |
| --- | --- |
| `NUXT_INITIAL_ADMIN_EMAIL` | 初期 admin のメールアドレス |
| `NUXT_INITIAL_ADMIN_PASSWORD` | 初期 admin のパスワード |
| `NUXT_INITIAL_ADMIN_NAME` | 初期 admin の表示名（省略時 `admin`） |
| `NUXT_SESSION_PASSWORD` | セッション暗号化キー（32文字以上）。開発時は未設定なら自動生成 |
| `NUXT_LLM_PROVIDER` | AI 読み取りのプロバイダ。`gemini` または `claude`（省略時 `gemini`） |
| `NUXT_GEMINI_API_KEY` | Gemini API キー。未設定でも起動でき、AI 読み取りはエラー表示になり手入力で登録できる |
| `NUXT_GEMINI_MODEL` | Gemini のモデル名（省略時 `gemini-3.8-flash`） |
| `NUXT_ANTHROPIC_API_KEY` | Anthropic API キー（`NUXT_LLM_PROVIDER=claude` のとき使用）。未設定だと AI 読み取りはエラー表示になり手入力で登録できる |
| `NUXT_ANTHROPIC_MODEL` | Claude のモデル名（省略時 `claude-opus-5-5`） |

- データは `./data` に保存されます（SQLite DB `data/app.db` と元画像 `data/uploads/`）。再起動後も保持されます。`data/` は git 管理外です。
- DB マイグレーションは起動時に自動適用されます。
- 初期 admin は、DB に admin が1人もいない場合に限り、起動時に環境変数から作成されます。

テスト: `npm test`（Vitest）

## 使用技術

- Nuxt 3（Vue 3 / TypeScript）: フロントとサーバー API を1プロセスで動かし、起動手順を最小にするため
- SQLite（better-sqlite3）+ Drizzle ORM: ファイル DB で外部サービス不要。型安全なクエリとマイグレーション
- nuxt-auth-utils: パスワードハッシュ化と HttpOnly Cookie セッション（ログアウト時は利用者ごとのセッション世代を進めてサーバー側でも失効させる）
- zod: API 入力の検証
- Vitest: ユニットテスト

## AI モデル

- **Gemini `gemini-3.8-flash`**（Google Gen AI SDK `@google/genai` の Interactions API、thinking level `low`）。`NUXT_GEMINI_MODEL` で変更できます。
  - 選定理由: LLM プロバイダは未定のため、開発中は個人キーで使える Gemini で検証しています。当初は低コストの `gemini-3.5-flash-lite` を既定にしていましたが、端が切れて読めないメールアドレスを補完してしまう（推測で補完しない要件に反する）ことがあり、プロンプトでの対策だけでは安定しませんでした。`gemini-3.8-flash` では提供画像10枚×2回の評価で補完が0件だったため、こちらを既定にしています（名刺1枚あたりの費用はどちらも1円未満）。
- **Claude `claude-opus-5-5`**（公式 SDK `@anthropic-ai/sdk` の Messages API、構造化出力 `output_config.format`、effort `low`）。`NUXT_LLM_PROVIDER=claude` と `NUXT_ANTHROPIC_API_KEY` を設定すると切り替わり、`NUXT_ANTHROPIC_MODEL` でモデルを変更できます。安全分類器による拒否時はサーバー側フォールバック（`fallbacks: "default"`）で既定の代替モデルに再実行させ、それでも拒否された場合は読み取り失敗として表示します。
  - Anthropic の API キーが手元になかったため、Claude 経路は SDK をモックしたユニットテスト（リクエストの形・出力の整形・拒否やエラーの扱い）でのみ確認しており、実 API での読み取りは未確認です。
- 構成（`server/lib/extract/`）: プロンプト・JSON スキーマ・出力の検証はプロバイダ共通（`schema.ts`）、プロバイダ固有の呼び出しは1ファイルずつ（`gemini.ts` / `claude.ts`）に閉じ込め、`index.ts` が `NUXT_LLM_PROVIDER` で切り替えます（既定は Gemini）。
- 推測・補完の防止:
  - プロンプトで「印刷されている文字だけを書き写す」「記載なし・読み取れない項目は空文字」「メールのドメインから Web サイトを作らない、記載のない郵便番号を補わない等の補完禁止」「表記は記載どおり」を指示しています。
  - 出力は JSON スキーマ（8項目すべて文字列・必須）で受け、サーバー側でも検証します（文字列以外・欠落は空欄、前後空白の除去、長さ制限、メールアドレス／URL の形でない値は空欄）。
- API キーはサーバー側の `runtimeConfig`（非 public）でのみ扱い、ブラウザーには渡しません。画像はプロバイダ側に保存させない設定（`store: false`）で送ります。
- エラー時（キー未設定は 503、タイムアウト30秒・プロバイダエラー・解釈できない出力は 502）は画面に失敗を表示し、再読み取りまたは手入力で続行できます。
- 実際の API 呼び出しは、個人の Gemini API キー（課金有効プロジェクト = Paid Services。入力は Google の製品改善に使われない）で確認済みです（2026-10-28）。結果は「動作確認の手順と結果」を参照。

## 対応画像形式

- JPEG / PNG / WebP、1ファイル 10MB まで、1枚ずつ取り込み
- 形式は拡張子や申告 MIME ではなく、ファイル先頭のマジックバイトで判定します（`server/lib/image.ts`）。
- 元画像は public 配下ではない `data/uploads/` に保存し、閲覧権限チェック付きの API（`/api/cards/:id/image`）経由でのみ配信します。

## 初期 admin の設定方法

`.env` の `NUXT_INITIAL_ADMIN_EMAIL` / `NUXT_INITIAL_ADMIN_PASSWORD`（任意で `NUXT_INITIAL_ADMIN_NAME`）を設定して起動します。admin が既に存在する場合は作成されません（値を変えても既存 admin は更新されません）。未設定のまま起動するとログに警告が出るので、設定して再起動してください。

## 利用者の追加方法

admin でログインし、「利用者・閲覧許可」画面（`/admin/users`）でメールアドレス・表示名・初期パスワード（8文字以上）を入力して追加します。

- 追加される利用者の role は常に `user` です（API は role を受け取りません）。
- 初期パスワードは admin が設定し、利用者に別途伝えます（招待メール・パスワード再設定メールは未実装）。利用者はログイン後に「アカウント設定」で自分のパスワードに変更できます。

## 確認用アカウントの利用方法

確認用アカウントの情報は当日共有します。

## role・閲覧許可の設定方法

### role の変更

admin で `/admin/users` の利用者一覧から、各行の「admin に変更」/「user に変更」を押し、画面内の確認で「変更する」を押します（API: `PATCH /api/admin/users/:id/role`、`{ role: 'admin' | 'user' }`）。

- admin のみ実行できます（user は 403）。user が自分の role を変えることはできません。
- **admin も自分自身の role は変更できません**（400）。自分を締め出す事故を防ぐためで、自分の行には操作ボタンを出しません。
- **admin が0人になる変更は拒否します**（400）。admin 数の確認と更新を1つのトランザクション（`BEGIN IMMEDIATE`）で行い、2人の admin が同時に互いを降格するような操作でも0人にならないようにしています。なお API を呼べるのは admin だけなので、admin が1人のときの対象は必ず自分になり、上の「自分の role は変更不可」で先に拒否されます。
- 存在しない利用者は 404。
- **反映は即時**: サーバーの権限判定は毎リクエスト DB の role を読むため、対象者の次のリクエストから新しい role で判定されます（再ログイン不要。降格された利用者の既存セッションも、次のリクエストから admin API は 403）。
- **閲覧許可の扱い**: user を admin に昇格しても付与済みの閲覧許可は DB に残ります（admin は全件閲覧のため、admin の間は使われません）。user に戻すと、残っていた許可が再び効きます。

### 閲覧許可

admin で `/admin/users/:id`（利用者一覧の「閲覧許可を設定」。role が user の利用者のみ）を開き、その利用者に閲覧許可を付与・解除します。

| 許可の種類 | 閲覧できる名刺 |
| --- | --- |
| 企業 | 指定した企業の全名刺 |
| 部署 | 指定した企業の指定した部署の名刺（企業とセット） |
| 人物 | 指定した人物（名刺に記載された相手）の名刺 |

許可がない user は自分が登録した名刺のみ閲覧できます。

## パスワードの変更・再設定

- **本人による変更**: ヘッダーの利用者名または「アカウント設定」（`/account`）で、現在のパスワード・新しいパスワード・確認用を入力します（各欄は伏せ字で「表示/隠す」切り替えあり）。API は `POST /api/auth/password`（`{ currentPassword, newPassword }`）。
  - 現在のパスワードが誤っていれば 400（「現在のパスワードが正しくありません」。ログイン切れの 401 と区別するため 400）。新しいパスワードは8文字以上で、現在と異なること。
  - 変更すると、その利用者の**他のセッション（他の端末・ブラウザー）はすべて失効**し、操作したセッションだけが新しい世代で発行し直されるためログインしたままになります。
- **admin による再設定**: `/admin/users` の各行の「パスワード再設定」から新しいパスワードを入力し、画面内の確認で「再設定する」を押します（API: `POST /api/admin/users/:id/password`、`{ newPassword }`）。
  - admin のみ（user は 403）。自分自身は対象外（400。自分は本人による変更を使う）。
  - 再設定すると、対象者の**既存セッションはすべて失効**します（新しいパスワードを admin から本人に別途伝える運用）。
- **セッションの失効の仕組み**: 利用者ごとに `sessionVersion`（セッション世代）を DB に持ち、ログイン時にその値をセッション Cookie（暗号化）に入れます。`requireUser` は毎リクエスト Cookie の世代と DB の世代を比較し、異なれば 401 にして Cookie を消します。ログアウト・本人のパスワード変更・admin による再設定で世代を1つ進めるため、それ以前に発行された Cookie はすべて使えなくなります（本人の変更時のみ、操作中のセッションを新しい世代で再発行）。

## 権限設計

- **判定はサーバー側の1か所に集約**: `server/lib/access.ts` の `accessScope` / `canView` / `scopeWhere` が「閲覧できる名刺」の条件を作り、一覧・検索・詳細・元画像取得のすべてがこれを経由します。画面上の非表示には依存しません。
- admin は全件。user は「自分が登録した」「企業の許可」「部署の許可」「人物の許可」の**いずれか1つ**を満たせば閲覧可。許可を1つ解除しても、別の許可や登録者権限が残っていれば閲覧できます。
- **権限のない名刺は 404**: 存在しない ID と区別できないようにし、名刺 ID の存在を漏らしません。
- **登録者はセッションから取得**: リクエストボディの値は使わないため、登録者の偽装はできません。
- **role は毎リクエスト DB から読む**: セッション内の role を信用しないため、変更・削除が即時反映されます。role・許可を変更する API は admin チェック必須です。
  - 画面表示用（ヘッダーの role 表示・`/admin` への遷移ガード）には Cookie 内の利用者情報を使いますが、これは role 変更後に古くなり得ます。そこで (1) `requireUser` が Cookie 内の role・表示名・メールが DB と食い違っていれば Cookie を更新し、(2) 画面のルートミドルウェアがログイン中は遷移のたびに `GET /api/auth/me`（DB が正）を呼んでクライアントの状態を更新します（初回表示は SSR 時に取得した値を使うので二重には呼びません。失効していれば `/login` へ）。いずれも表示のためで、サーバー側の認可は常に DB の role で行います。
- **企業・部署の正規化と ID 参照**: 会社名・部署名は NFKC 正規化 + 空白除去 + 小文字化したキーで既存レコードに紐付けます（全角/半角・空白・大文字小文字の揺れを吸収）。部署は企業に従属するレコードで、許可は文字列ではなく ID を参照するため、**他社の同名部署には許可が広がりません**。
- **人物の同一性**: 「正規化した氏名が同じ」**かつ**「メールアドレスが同じ」場合のみ同一人物とみなし、それ以外は別の人物レコードを作ります。人物の許可は人物 ID を参照するため、**同姓同名の別人には広がりません**。
  - トレードオフ: メールアドレスのない名刺が2枚ある場合、同じ人でも別人として扱われます（人物の許可はそれぞれに付与が必要）。権限が漏れる方向より、狭くなる方向に倒す判断です。
- **名刺の編集・削除は登録者本人と admin のみ**: `server/lib/access.ts` の `canEdit`（admin または `createdBy` が本人）で判定します。閲覧許可（企業・部署・人物）は「見る」権限であり、許可で見えるだけの名刺は編集・削除できません。
  - 見えない名刺への編集・削除は 404（閲覧と同じく存在を漏らさない）、見えるが編集権限がない場合は 403、未ログインは 401。
  - 詳細 API・一覧 API は `canEdit` を返し、画面はこれで編集・削除ボタンの表示を切り替えます（判定自体はサーバー側で毎回行う）。
  - 編集できるのは8項目のみです。登録者（`createdBy`）は変更できず、ボディに含めても無視します。元画像は登録時の記録として保持し、編集では差し替えできません。
  - 編集時は登録時と同じ処理（`server/utils/card-entities.ts` の `resolveCardEntities`）で企業・部署・人物を引き直します。会社名・部署名を変えると企業・部署の許可の対象も移ります（例: 会社名を変えると、元の企業の許可だけで見ていた利用者からは見えなくなる）。
  - 人物: 氏名・メールアドレスの正規化値が変わらない編集では人物 ID を維持します。氏名またはメールを変えると人物を引き直すため、**元の人物 ID への人物許可ではその名刺が見えなくなる**ことがあります（別人に変わった可能性があるため、許可を引き継がない側に倒す仕様）。
  - 削除は名刺レコードと元画像ファイルを物理削除します（DB の削除が成功してから画像を消す）。企業・部署・人物レコードは閲覧許可から参照されうるため残します。

## 動作確認の手順と結果

### 自動確認（E2E スクリプト）

アプリを起動した状態で、別のターミナルから実行します（追加の依存なし。Node.js の `fetch` で API と SSR 画面を叩きます）。

```bash
npm run dev                                   # 別ターミナルで起動しておく
node scripts/verify-e2e.mjs                   # 既定の接続先は http://localhost:3000
node scripts/verify-e2e.mjs --base http://localhost:3206   # 接続先を変える場合
```

- admin の認証情報は `.env` の `NUXT_INITIAL_ADMIN_EMAIL` / `NUXT_INITIAL_ADMIN_PASSWORD` から読みます。
- 実行のたびに一意な接尾辞付きの**架空データ**（利用者 7 名、名刺 14 枚（うち 2 枚は削除の確認で消える）、企業 5 社など）を作るため、同じ DB で何度でも再実行できます。確認用データは DB に残ります。
- 各チェックを `PASS` / `FAIL` で表示し、最後に件数を集計します。FAIL が1件でもあれば終了コード 1 です。
- 永続化の確認: 通常実行の最後に、作成した名刺・利用者・許可の ID を OS の一時ディレクトリ（`meishi-verify-e2e.json`）に書き出します。サーバーを停止・再起動してから `node scripts/verify-e2e.mjs --check-persist` を実行すると、それらが残っているかを確認します。

### 手動確認（ブラウザー）

評価者がブラウザーで確認する場合の手順です。名刺画像は手元の任意の JPEG / PNG / WebP を使えます（AI 読み取りを使わない場合は各項目を手入力）。

1. `/login` で初期 admin としてログインする（未登録メール・誤ったパスワードではエラーになることも確認）
2. 「名刺を登録」で画像を選び、元画像と抽出結果（または空のフォーム）を見比べて修正し、登録する → 詳細画面に遷移する
3. 「名刺一覧」で氏名・会社名の一部を入力して検索し、詳細画面で連絡先と元画像が表示されることを確認する
4. 「利用者・閲覧許可」で user を 2 名（例: A・B、メールは `example.test` などの架空ドメイン）追加する
5. ログアウトして A でログインし、名刺を数枚登録する（同じ会社の別部署、別会社の同名部署、同姓同名でメールが違う人物を含めると確認しやすい）
6. B でログインし、一覧が B 自身の名刺のみであること、A の名刺の `/cards/:id` や `/api/cards/:id/image` を直接開いても表示されないことを確認する
7. admin で `/admin/users` → B を選び、企業・部署・人物の許可を付与する。B の一覧に該当する名刺だけが出ること（他社の同名部署・同姓同名の別人は出ないこと）を確認する
8. 許可を解除し、B の一覧から消えること（別の許可が残っている名刺・B 自身の名刺は残ること）を確認する
9. A で自分の名刺の詳細を開き「編集」→ 項目を修正して「保存」すると反映されること（元画像はそのまま）、氏名を空にすると保存できないことを確認する
10. B に A の名刺の企業許可がある状態で、B の詳細画面に「編集」「削除」ボタンが出ないことを確認する。A が会社名を別の会社に変えると B から見えなくなることも確認できる
11. A（または admin）で「削除」→ 画面内の確認で「削除する」を押すと一覧に戻って完了メッセージが出て、その名刺が一覧から消え、`/api/cards/:id/image` も開けないことを確認する
12. admin で `/admin/users` から B を「admin に変更」し、B の画面で（再ログインなしに）ページを移動すると全名刺と「利用者・閲覧許可」が表示されることを確認する。「user に変更」で戻すと、B の次の操作から管理画面に入れず、許可の範囲の名刺だけに戻ることを確認する（自分の行には操作ボタンが出ないこと）
13. B で「アカウント設定」を開き、パスワードを変更する（現在のパスワードを誤るとエラー）。別のブラウザー（またはシークレットウィンドウ）でログインしていた B のセッションがログアウト扱いになり、変更した画面はログインしたままであることを確認する
14. admin で `/admin/users` から A の「パスワード再設定」を行い、A の既存セッションがログアウト扱いになり、新しいパスワードでログインできることを確認する
15. サーバーを停止・再起動し、名刺・画像・利用者・role・許可が残っていることを確認する

既定モデルでの項目別（2回合計）: 氏名 19/20、会社名・メール・電話・住所・Web 各 20/20、部署・役職 各 18/20。
残る不一致: 部署と役職の境界が曖昧な1枚（2回とも）、氏名の1文字の読み違い（1回）。

補完対策として追加したプロンプトの指示: 端で切れている・隠れている・ぼやけていて一部しか読めない項目は項目全体を空欄にする、見えている部分から残りを補わない、出力前に各値の全文字が画像上で見えているか確認する。flash-lite ではこの指示で補完が減った一方、反射のある項目まで空欄にする（慎重になりすぎる）揺れが出たため、モデル自体を変更した。
再現手順: `npm run dev` を起動した状態で `node scripts/eval-extract.mjs --images ./images --expected ./expected`。

ユニットテストでは、権限判定について以下を確認しています（`tests/access.test.ts`、データはすべて架空）:

- admin は全件 / 許可なし user は自分の名刺のみ
- 企業許可、部署許可（他社の同名部署に広がらない）、人物許可（同姓同名の別人に広がらない）
- いずれか1つの許可で閲覧可、1つ解除しても別の許可が残れば閲覧可、許可解除後も登録者は閲覧可
- 編集・削除（`canEdit`）は admin と登録者のみ。閲覧許可で見えるだけの名刺は編集不可
- `scopeWhere` をインメモリ SQLite（実際のマイグレーションを適用）に対して実行し、`canView` と同じ結果になること

## 制約・未実装・未確認の事項

- Claude による情報抽出は、API キーがなかったためモックしたユニットテストでのみ確認（実 API での読み取り精度は未確認）
- 部署と役職の境界が曖昧な名刺では、AI の振り分けが期待結果と異なることがある（確認画面で修正する前提）
- 読めない部分の補完はプロンプトとモデル選定で評価上 0 件にしたが、LLM の出力は確率的なため完全には保証できない（確認画面で利用者が確認・修正する前提）
- 名刺の編集で元画像は差し替えできない（登録時の記録として保持）。更新日時・編集履歴は記録していない
- 名刺を削除・編集しても、使われなくなった企業・部署・人物レコードは残る（閲覧許可が参照しうるため）
- 利用者の削除・表示名の変更は未実装
- パスワード再設定メール・招待メールは未実装（再設定は admin が画面で行い、本人に別途伝える）
- 「最後の admin は降格できない」判定は、HTTP からは決定的に再現できない（admin が1人なら対象は必ず自分になり、自分の role 変更として先に拒否される）ため、ユニットテスト（`tests/account.test.ts`）で確認している
- 画面の操作（画像選択・確認フォームの入力・許可の付与ボタンなど）はブラウザーで手動確認する前提で、E2E では API と SSR の HTML のみ確認している
